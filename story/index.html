Continuous policy search for long-horizon tasks: Astra agents design, evaluate, and improve executable Methods for Factorio (and Civilization V)

We asked Astra to improve a Factorio repair procedure. Then we tested it on twenty new factories.

Why save the procedure?

We wanted to test whether Astra could improve a way of working and reuse it on new tasks. Factorio gave us a long task with a clear outcome: connect mines, belts, machines, fuel, and power until the factory works. Our original aim was a rocket launch from a fresh world. We started smaller.

A Method is a file that defines executable steps. The Method runner executes those steps, which can use code or an AI agent. Saving the procedure lets the next agent use and change it without reconstructing the whole approach from a chat.

A policy is the set of rules that turns observations into actions. Policy search means testing and revising those rules. Here, Astra changed code and prompts; model weights stayed the same.

Method specificationOriginal goals

Start small. Then repeat.

The first task was to make twenty new iron plates. Direct Astra and a fixed Method each passed two maps. We then tested the checker with broken factories and inspected saved games to confirm the results.

The first recorded search stopped during setup: parallel game windows failed to connect. We removed screen recording from optimization and ran two game worlds without visible windows. The real game engine still ran; traces and saves kept the evidence. We could record selected repairs later.

The first completed search chose among procedures written before any game feedback. Five contenders played three development maps each. A code Method won, then ran against the initial agent Method on two unseen maps.

Next, Astra repeatedly read the results and wrote new versions. This produced 16 revisions and 57 attempts: 52 passes and five failures. The policies reused observations, removed extra actions, changed belt routes, and reduced the coal loaded. Astra wrote the code between games; the code ran without model calls during play.

A fixed program could already solve this small task quickly. We moved to varied repairs to ask a different question: could a searched Method help the same Astra model on new factories?

Early tests and failed attempts

A separate Factorio Learning Environment connection also passed two initial maps. These small tests did not establish a stable ranking. The recorded search used all twelve setup attempts; six concurrent graphical clients failed to join in time. No policy trial was scored.

The later supplied-kit task required five new plates and five newly mined ore in each of three fixed windows, with no actions during measurement. Thirteen candidate and baseline documents existed before feedback. The continuous search then added versions p12–p27. Failures included incorrect action batches and a game process lost before its required save. All records were kept.

First testsFull search record

Repair thirty different factories.

The harder task was to restore production of red and green science: game items made through several connected production lines. We varied the layouts and faults. Each factory had game evidence that it worked before damage, failed after damage, and could be repaired legally.

Ten factories were available for policy development. Twenty stayed hidden from the author. We saved the chosen Method and made no further changes before that final test.

Direct Astra got the task and tools. The Method added the procedure developed on the first ten factories. Both faced the same outside checker.

To pass, a factory had to mine fresh ore, make the required intermediate items, and produce and retain new science across three measurement windows. The checker first cleared stored materials and crafting progress, allowed a warm-up, and later inspected the saved game independently.

Three agent stages became one.

The first repair Method used separate agents to diagnose, repair, and check the factory. The first stage often ran out of time without a useful handoff, and later agents repeated work.

Astra changed the procedure: code read and shortened the factory map, then one agent handled the repair. Four versions ran in 31 Method attempts, alongside ten direct baseline attempts.

How the replays were made

Saved equipment changes were replayed on copies of the original broken saves. Accepted and rejected actions, and the final equipment layout, matched. Action spacing and game speed were edited. Model thinking and observation calls are omitted. No new model calls or scored attempts were made.

Less time and input.
Both repaired every factory.

The selected Method and direct Astra each restored production in all twenty unseen factories. On the eighteen pairs where both passed every rule, the Method used 23% less median full time. Across all twenty attempts, it used 56% fewer input tokens—the units used to count model input, including cached input.

Direct Astra made unsupported tool requests in two cases. Its strict score was therefore 18/20, versus the Method’s 20/20, although both factories were repaired.

What may explain the gain?

The Method gave the agent less text to read and used fewer shell commands: 118 versus 191. It used slightly more game actions, 213 versus 205. Better input preparation and less repeated work may explain the time reduction, but we have not tested those changes separately.

Final reportChart data

Civ VI exposed a setup mistake.

We next tried a longer task in Civilization VI: found and grow two cities, reach twenty science per turn, and keep the economy stable for five rounds, within 35 turns.

We did not run it through the Method CLI. The runner passed a written strategy to Astra through Codex. Seven games ran and their saved states were checked, but they did not test the Method system we intended to test.

The pilot is complete. A valid Method execution test, more maps, and combat tasks remain unfinished.

What the written-strategy pilot measured

Every game started from the same prepared Roman capital, with one Warrior, Scout, and Builder, 50 gold, and three technologies. There were no enemy civilizations, city-states, barbarians, or tribal villages. Each attempt allowed twenty minutes and 1,500 game requests.

Astra wrote three strategies and tested each once. The first succeeded in 31 turns; the second needed 33; the third failed to hold the conditions for five rounds. The first strategy was kept for four fresh comparison games.

What to test next

Which changes caused the gain?

Give direct Astra the same compact map, then the same repair prompt. Compare code alone, an agent alone, and their combination.

Does it work on new cases?

First confirm the exact Method file runs through the intended CLI. Then test new maps, fault combinations, and faults that appear during play. Keep the selected procedure unchanged for the final test.

Does reuse repay the search cost?

Count authoring and failed trials alongside execution. Measure how many later runs are needed to repay the search effort.

The useful result is a procedure we can inspect, change, and test again.

Software repair, data cleanup, and other tasks with clear end checks could be next applications.

Evidence and limits

What the Factorio comparison establishes

This is one generated factory family. It does not show that direct Astra could not perform the repairs, that model calls are necessary, or that Methods beat fixed programs. We did not achieve the original fresh-world rocket launch.

The two-case strict-score difference does not establish a reliable success-rate gain (exact paired test: p = 0.5). Service latency and local load can affect time. Code and prompts changed together, so the study does not isolate an advantage from the Method file format.

Uncached input fell from 915,259 to 594,730 tokens, about 35%. Output fell from 31,207 to 27,998. The subscription dollar cost is unknown. Search cost is separate: 31 Method games and 51 agent sessions, plus authoring and setup. Ten early sessions lack final usage, so total search tokens are unknown.

Execution and verification details

The repair policies ran through Method v3. A code step called the fixed Codex subscription helper for a fresh Astra agent session. That session could contain several model turns and tool calls.

The production rules stayed fixed. A development test found a JSON export fault that hid furnace recipe names. A versioned reader recovered the exact recipe objects from original native saves. The same reader was applied to every attempt and frozen before the final tests. Original records were retained; no player was rerun to replace a result.

All forty final evidence audits and 54 focused repair tests passed. The checker was outside the playing interface. Trusted Method code was reviewed to use public observations; complete operating-system isolation is not claimed.

What we built and what we used

This work added game adapters, task checks, trial and search tools, candidate Methods, cases, reports, and demo replays. The public Method v3 specification and executor were developed in the related hackathon work.

Existing foundations were Method’s earlier product and SDK, Factorio, the Factorio Learning Environment, Civilization VI, OpenAI models, and Codex. Raw game saves, recordings, and private logs remain outside Git.
