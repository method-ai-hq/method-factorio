01 / THE QUESTION

One good answer.
Or a better way to act?

We started with a question from the Method brainstorm: can Astra invent useful procedures for long tasks, where success is clear at the end but the value of each move is hard to measure?

A game makes this concrete. In Factorio, a player must connect mines, belts, machines, fuel, and power. Each part can look correct while the whole factory still fails. Our first ambition was a rocket launch from a fresh world. We began with smaller tasks so we could trust the game tools and the checks.

A Method is a saved procedure an agent can run again. It can contain code, model calls, tool use, loops, and checks. It keeps useful work outside a single chat, so a later agent can inspect it, test it, change it, and build on it.

Here, a policy means the rules that turn what the agent sees into what it does next. Policy search means testing and changing those rules. We changed procedures and prompts, not model weights.

This is the point of Methods: make the procedure an object we can improve, rather than asking each new agent to work out the whole approach again. The test is whether that saved work helps on a new case.

02 / FIRST CONTACT

First, make the result
mean something.

Before searching for better policies, we had to show that an agent could control the real game—and that the checker could tell a working factory from a broken one.

START SMALL

Make 20 new iron plates.

Direct Astra, a fixed Method, and a separate FLE connection each passed two fresh maps. These six small runs checked the basic tools. They were too few, and too affected by timing, to establish a stable ranking.

CHECK THE CHECKS

Break the factory on purpose.

Later controls tested empty worlds, stored ore, broken belts, reversed inserters, missing fuel, and incomplete production windows. A model saying “done” could never count as a win. We also saved and inspected the native game state.

FIRST STOP

Recording blocked the first search.

The first Method v3 job used all 12 allowed setup attempts. Six parallel graphical clients failed to join in time. The live checks were incomplete, so no policy trial was scored. That run produced no winner.

CHANGE THE SETUP

Search without a screen. Record later.

We removed recording from policy optimization. Two headless worlds could run at once, with game traces, exact checks, and terminal saves. A separate demo could later replay selected actions in the visible game.

“Headless” means the game runs without its visible window. It does not mean the result is simulated by a model. The real Factorio engine still runs the factory.

The early lesson was practical: a search loop needs reliable tools, fixed checks, and a way to recover from setup faults. Parallel work helps only after each worker can run and produce valid evidence.

03 / SEARCH, THEN REPEAT

Choosing a policy
is only the beginning.

The first completed headless comparison used a small supplied kit: build a drill → belt → inserter → furnace line. To pass, it had to make at least five new plates and mine five new ore in each of three fixed windows. The agent could not act during measurement.

Thirteen Method documents had been written before game feedback. Five contenders then played three development maps each. An existing code policy, p10, was selected. On two unseen maps, both the initial agent Method and p10 passed.

We then made the loop explicit: let Astra keep reading the results and writing new Methods. That produced 16 new versions, p12 through p27, across 57 attempts. Of those attempts, 52 passed and five failed. All new policies used code during play; Astra did the reasoning between trials.

The changes were concrete: reuse an observation, remove extra rotations, change movement and belt routes, repair faulty batches, reduce the coal loaded, and add checks for actual production. Failed versions stayed in the record.

Search did not produce a smooth upward line. One version sent the wrong batch of actions. Another attempt lost its game process before the required save. A later version added a production check, with more actions. A better procedure depends on what we measure.

The small task also exposed a limit in our original idea: a fixed program could already solve it quickly. We had not found a task that needed a model during execution. The next question became more useful: can a searched Method help the same Astra model on unseen, varied tasks?

04 / A HARDER TEST

Give it a broken factory.
Keep the answer hidden.

We moved to factories that make red and green science. These need several connected production lines. Each test started with a damaged factory. The agent had to find and repair faults in equipment, routes, fuel, or power.

We built 30 cases. Each had native game evidence that the healthy factory worked, the damage stopped it, and a legal repair could restore it. The layouts and faults varied, while the goal and checker stayed the same.

Direct Astra received the task and tools, then worked out its approach. The Method received a procedure that Astra had improved on the ten development factories. The author could not see the final cases. We froze the chosen version before the final comparison.

The checker cleared stored materials and crafting progress, allowed a warm-up, then measured three production windows. The factory had to mine fresh iron and copper, make the required intermediate items, and produce and retain new red and green science. A separate read checked the saved game.

Was the validator fixed?

The production rules stayed fixed. During development, a JSON export fault hid some furnace recipe names. A versioned reader recovered the exact recipe objects from the original native saves. The same reader was applied to every attempt and frozen before the final tests. Original records were kept. No player was rerun to replace a result.

All 40 final evidence audits and 54 focused repair tests passed. The checker was outside the playing interface. Trusted Method code was reviewed to use public observations; complete operating-system isolation is not claimed.

05 / HOW THE POLICY CHANGED

The big gain was
less repeated work.

The repair search tested four versions in 31 Method game attempts. Ten direct baseline attempts ran on the same development set. Astra used the results to revise the procedure, then tested the next version.

The first Method split work across three fresh agent stages. The final Method used code to prepare a compact map, then gave one agent a clear repair job. Select a version below to see what changed.

On one retained map, the compact representation reduced an initial observation from 112,008 to 17,908 characters. It kept the geometry needed for repairs. The prompt also made the route to completion clearer. Direct Astra could write code too, but did not receive this searched helper or prompt.

06 / THE UNSEEN FACTORIES

Same model.
A better prepared procedure.

The final test used twenty new factories. Both approaches restored production in all twenty. The Method took less time and used fewer input tokens in this test family.

Its strict score was 20/20, versus 18/20 for direct Astra. The two direct failures were unsupported tool requests, even though the factories were repaired. This is evidence of a useful procedure—not evidence that direct Astra could not solve the repairs.

Why might it be faster?

The trace fits a simple explanation: the agent had less text to read and fewer command steps to repeat. Across the final runs, the Method used 118 completed shell commands, versus 191 for direct Astra. Yet it used slightly more game actions: 213 versus 205.

So the gain does not appear to come from doing fewer repairs. A likely source is better preparation and less repeated reasoning around the game. We have not yet tested each change alone, so we cannot assign the gain to a single cause.

What these numbers do—and do not—establish

The 56% input reduction includes cached input. Uncached input fell from 915,259 to 594,730 tokens, about 35%. Output tokens fell from 31,207 to 27,998. Token counts are not a dollar bill: the subscription cost is unknown.

Search had a separate cost: 31 Method game attempts and 51 agent sessions, plus authoring and setup. Ten early sessions lack final usage, so total search tokens are unknown. We have not shown how many future uses would repay that cost.

The two-case strict-score difference is too small to establish a reliable success-rate gain (exact paired test: p = 0.5). Service latency and local load can affect time. This study does not show that Methods beat deterministic programs, solve arbitrary Factorio tasks, or need several model agents.

The procedure changed together with its code and prompt. This comparison does not isolate an advantage from the Method file format itself. It tests the value of a searched procedure, executed as a Method.

08 / ANOTHER KIND OF LONG TASK

From factory repair
to Civilization VI.

Work in progress · snapshot at 21:05 UTC, 10 September

Factory repairs give quick feedback. Civilization VI adds turns, growth, delayed rewards, and choices that compete for the same resources. A move can look good now and cause a shortage several turns later.

The current economy task starts from a prepared Roman capital. Found two new cities, grow each to at least three people, and reach at least twenty science per turn. Keep gold and food conditions valid across all three cities for five full rounds, within 35 turns.

Two earlier direct-agent calibration runs reached the task condition in 35 and 33 turns. These are not an unseen-case comparison. The pilot now tests a written Method given to a fresh agent; it is separate from the Factorio Method v3 execution study.

The small matched comparison has now finished. Both approaches passed both runs. The Method used slightly fewer turns, but more playing time, game requests, and model tokens. It did not show a consistent advantage. The original v1 remained best; the two later versions did not beat it in development.

A combat task is also being prepared: capture a target city, keep the starting cities, and hold the target for five rounds. It has no certified result yet. Neither task is a full Civilization victory.

09 / WHAT COMES NEXT

Make the claim stronger.
Then make the task harder.

The next step is to find where the saved procedure helps, where it stops helping, and what part causes the gain.

01

Test each part alone.

Give direct Astra the same compact map, then the same repair prompt. Compare code only, agent only, and their combination. This will show which parts earn their place.

02

Keep a new test set private.

Use more layouts, unseen fault combinations, and repeated matched runs. Freeze each selected policy before opening the final cases. Report repair success separately from request-rule failures.

03

Add change during play.

Test new faults, resource shortages, and goals that change after work begins. Ask whether an agent step can handle new information that a fixed repair script misses.

04

Measure the cost of learning.

Count authoring, failed trials, and search as well as execution. Then measure how many uses of the selected Method are needed to repay the search effort.

05

Carry the process into other work.

Complete the Civ VI checks, then test new maps and combat. Beyond games, try software repair, data cleanup, and operational tasks with clear end checks. These are possible applications, not results from this study.

The takeaway

Keep what the agent learns about the work.

In this experiment, a searched procedure helped the same model handle unseen factories with less time and input. The broader promise of Methods is a way to preserve, test, and improve that procedure—while keeping the evidence that tells us whether it works.

10 / NOTES & EVIDENCE

A record you can inspect.

This page separates the initial ambition, measured results, and proposed next steps. We did not achieve a fresh-world rocket launch, a full Civilization victory, or proof that policy search is the only way to solve these tasks.
